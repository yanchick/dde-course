# Семинар 5 — Сложная предобработка и трансформация

**Связанная лекция:** [Сложная предобработка и трансформация](../lectures/04-transformation.md)

## Цель

Продолжить путь `bronze → silver → gold`: собрать признаки витрины продаж,
подготовить временной ряд, сравнить три прогноза и оценить лексиконную
тональность. Отдельно — не протечь будущим и понять, что даёт
инкрементальный пересчёт.

ClickHouse и Airflow на семинаре не нужны: все задания — чистые вычисления
над функциями репозитория Sputnik-Mart.

## Результаты

- Студент считает rolling-признаки на 7 дней (`orders_7d`, `downloads_7d`,
  конверсию и средний чек) и доказывает, что окно не видит будущее.
- Строит лаги, скользящее среднее и суточные sin/cos для часового ряда.
- Сравнивает baseline, ручной AR(1) (AR-часть ARIMA(1,0,0)) и прогноз
  репозитория по MAE на одном тестовом окне.
- Оценивает лексиконную тональность на 30 отзывах и объясняет 8 ошибок.
- Опционально пишет 50 PGM P2-картинок `32×32` и читает их обратно.
- Проверяет, что пересчёт последних 7 дней даёт те же признаки, что и полный
  прогон по всей витрине.

## Задания

1. **5.1 Признаки витрины.** 5 датасетов × 14 дней, rolling 7 дней; проверка:
   70 строк без NaN, `max_event_dt ≤ dt`, первый день не знает будущего.
2. **5.2 Признаки ряда.** `lag_1`, `lag_7`, `rolling_24`, `hour_of_day`,
   `sin_hour`, `cos_hour`; проверка: 48 строк, ровно 7 null в `lag_7`, окно
   не смотрит вперёд.
3. **5.3 Прогноз.** MAE baseline, AR(1) и `forecast_series` репозитория;
   проверка: оба прогноза лучше baseline, тест — 12 часов.
4. **5.4 Тональность.** Лексиконный `score_text` на 30 отзывах; проверка:
   accuracy в `[0.60, 0.90]` и не меньше 3 содержательных ошибок.
5. **5.5 Бонус (P2).** 50 детерминированных PGM P2-картинок `32×32`;
   проверяются число файлов, размер и диапазон `[0, 1]`, но в 7 проверок не
   входят.

## Эксперимент

Пересчитать признаки последнего дня по всей истории и только по последним
7 дням. Результаты обязаны совпасть: окно короче истории. Обсуждаем, почему
pandas пересчитывает всё в памяти, а ClickHouse считает агрегаты по окну
инкрементально и когда такой пересчёт всё равно ломается (признаки по всей
истории, late-arriving data, окно шире backfill-диапазона).

## Как запускать

### Подготовка стенда

```bash
git clone https://github.com/yanchick/Sputnik-Mart.git ~/Sputnik-Mart
cd ~/Sputnik-Mart
uv sync --all-packages --dev
```

!!! info "ClickHouse и Airflow не нужны"
    Задания 5.1–5.4, эксперимент и бонус — чистые вычисления над функциями
    репозитория (`sim.sensors`, `validation.validator`, `transform.gold_*`).
    Поднимать `docker compose` не требуется: достаточно venv репозитория.
    `pandas` и `numpy` приходят из его зависимостей.


### Запуск из терминала

```bash
export SPUTNIK_REPO=~/Sputnik-Mart
# из корня репозитория
cd "code/seminars/05_transformation"

# студенческая версия (до выполнения заданий все 7 проверок FAIL — это ожидаемо)
uv run --project "$SPUTNIK_REPO" python seminar_05.py

```

`--with` не нужен: все импорты (`pandas`, `numpy`, `sim`, `validation`,
`transform`) уже есть в окружении репозитория.

!!! note "Скрипт импортирует код репозитория"
    Без `--project "$SPUTNIK_REPO"` (или вне venv репозитория) не разрешатся
    `sim.sensors`, `validation.validator` и `transform.gold_*`.


### Запуск в JupyterLab

```bash
cd ~/Sputnik-Mart
uv run jupyter lab
```

Откройте `seminar_05.py` как notebook (JupyterLab понимает percent-format).
Выполняйте ячейки сверху вниз. `SILVER` объявлена в блоке «Данные», а `MART`
и результаты шагов — в блоке «Прогон», поэтому ячейки можно запускать повторно.

### Ожидаемый результат

1. **Данные.** `silver` — 288 строк × 14 колонок, 6 станций; часовые
   агрегаты — 288 строк (по одной на станцию и час). Sparkline ряда
   `st_meteo-01 / TEMPERATURE` — 48 точек.
2. **5.1.** 204 заказа, 314 скачиваний, 20 подписок, 908 кликов; витрина —
   70 строк × 6 колонок; признаки — 70 строк. На первом дне каждого датасета
   `orders_7d` равен `orders` этого дня (будущее не подмешано).
3. **5.2.** Ряд температуры — 48 строк; `lag_7` пуст ровно в 7 первых
   строках; последний `rolling_24` равен среднему последних 24 значений.
4. **5.3.** Тест — 12 часов; MAE: baseline `13.1595`, AR(1) `5.5066`,
   repo `2.8692`. Оба прогноза лучше persistence.
5. **5.4.** Accuracy `0.7333` (22 из 30), 8 ошибок. Типичные промахи:
   «не рекомендую» → positive, «не понравилось» → positive, «ужасное
   качество, много ошибок» → neutral (основы гасят друг друга).
6. **5.5 (бонус).** 50 файлов PGM P2, все `32×32`, значения в `[0, 1]`;
   в 7 проверок не входит.
7. **Эксперимент.** Последний день `2026-09-14`: `full_rows=70`,
   `window_rows=35`, `equal=true`, `mismatches=0`.
8. **Воспроизводимость.** Два digest совпадают:
   `a694c4c1880d5b0d4a40494b891102d35caeae2956c6be51dfeda69ac1ee6d03`,
   печатается `REPRO_OK`.
9. Итог: `Итог: 7/7 проверок пройдено`.

!!! note "Про `orders` и подписки"
    `build_sales_rows` считает подписку покупкой, поэтому в витрине `orders`
    включает и заказы, и подписки. Числа `204` и `20` в консоли — это события
    по типам, а не колонка `orders` витрины.


!!! note "Почему 48 точек, а не 24"
    В `demo` 24 периода дают по одной точке на час в сутки — этого мало для
    `rolling_24` и `lag_7`. Семинар генерирует 48 часов (288 чтений), чтобы окна
    были содержательными. На данные стенда это не влияет: скрипт работает с
    локальным `sim`, а не с витриной `demo`.


!!! note "Почему AR(1), а не ARIMA из statsmodels"
    `statsmodels` в зависимостях репозитория нет, поэтому AR(1) реализован
    вручную: это AR-часть ARIMA(1,0,0) с `d=0`, `q=0`. Если поставить
    `--with statsmodels`, то `ARIMA` можно добавить четвёртой моделью и сравнить
    на том же hold-out; логика проверки не изменится.


!!! note "Почему 5.3 считается на `st_air-02 / NOISE`, а не на температуре"
    На `TEMPERATURE` окно 36/12 пересекает смену суточной фазы: AR(1) без
    сезонности честно проигрывает persistence (MAE больше baseline), и проверка
    «AR(1) лучше baseline» не выполняется. Для демонстрации берём стационарный
    ряд шума: там AR(1) действительно выигрывает, а repo-модель с sin/cos —
    ещё сильнее. Логика оценки при этом одинаковая для любого ряда.


### Если что-то не работает

| Симптом                                             | Что делать                                                                 |
| --------------------------------------------------- | -------------------------------------------------------------------------- |
| `ModuleNotFoundError: sim` / `validation.validator` | запускать через `uv run --project "$SPUTNIK_REPO"`                         |
| `ModuleNotFoundError: pandas`                       | `uv sync --all-packages --dev` в репозитории                               |
| `AttributeError` при работе с `dt`                  | в pandas 3 сравнение `Timestamp` с `date` запрещено — приводите к дате     |
| 5.3: `прогноз репозитория не покрыл тестовое окно`  | проверьте, что `silver_train` обрезан по `measured_at <= последний train`  |
| 5.2: `lag_7` не 7 null                              | ряд должен быть отсортирован по времени до `shift`                         |
| Кириллица в консоли ломается                        | `export PYTHONIOENCODING=utf-8`                                            |
| Бонус: нет файлов в `_out/images`                   | проверьте права на `BONUS_DIR` или задайте абсолютный путь                 |
| Студенческая версия печатает `0/7`                   | это ожидаемо до выполнения заданий; смотрите строки `Задание 5.x не выполнено` и `Эксперимент не выполнен` |
