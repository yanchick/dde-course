# Семинар 8 — Современные хранилища данных

**Связанная лекция:** [Современные хранилища данных](../lectures/07-storage.md)

## Цель

Разложить одно и то же чтение по трём хранилищам и понять, почему это не
дублирование: озеро хранит сырьё и промежуточные слои, колоночная витрина
отвечает на запросы, документная коллекция принимает разные схемы без
миграции. Отдельно — партиции, части MergeTree и цена чтения строки против
колонки.

MinIO, ClickHouse и Mongo на семинаре не нужны: DDL читается из репозитория,
а «озеро» моделируется словарём с теми же ключами, что у MinIO.

## Результаты

- Студент раскладывает 120 событий по `bronze → silver → gold` и объясняет,
  кто пишет и читает каждый слой.
- Пишет партицию идемпотентно: повторная запись не плодит объекты и не меняет
  отпечаток.
- Читает MergeTree DDL и показывает, что сентябрь и октябрь лежат в разных
  партициях, а сумма строк по частям равна факту.
- Считает стоимость чтения: 720 значений против 240 на одном запросе.
- Хранит двух провайдеров с разной схемой и достаёт метрику без миграции.
- Восстанавливает потерянную партицию и сверяет отпечаток.

## Задания

1. **8.1 Слои озера.** `build_lake_layers`: `bronze/{provider}/{dt}`,
   `silver/{dataset}/{dt}`, `gold/fact_readings/{dt}`. Проверка: 10 + 10 + 2
   партиции, по 120 строк в каждом слое, дата есть в каждом ключе.
2. **8.2 Идемпотентная запись.** `write_partition`: сортировка по `readingId`,
   NDJSON, перезапись ключа. Проверка: 10 объектов, 120 строк, повтор не меняет
   `checksum`.
3. **8.3 MergeTree.** `parse_merge_tree` и `simulate_parts`: движок,
   `PARTITION BY toYYYYMM(dt)`, `ORDER BY (station_id, metric, measured_at)`.
   Проверка: две месячные партиции, сумма строк 120.
4. **8.4 Колонки против строк.** `scan_cost` и `benchmark`. Проверка:
   `720`/`5760` байт против `240`/`1920`, `speedup=3.0`.
5. **8.5 Mongo.** `normalize_provider` и `query_metric`: `schema` у метео,
   `metrics[]` у воздуха. Проверка: разные наборы метрик читаются без миграции,
   отсутствующая метрика возвращает `None`.

## Эксперимент

Удаляем из «озера» объекты за `2026-10-01`. Пустеет только эта партиция,
соседний день цел — сбой локализован. Затем перезаписываем её из исходных
событий: 60 строк потеряно, 60 восстановлено, отпечаток совпал. Обсуждаем,
почему партиция — единица удаления и перезаписи, а не «папка для красоты».

## Как запускать

### Подготовка стенда

```bash
git clone https://github.com/yanchick/Sputnik-Mart.git ~/Sputnik-Mart
cd ~/Sputnik-Mart
uv sync --all-packages --dev
```

!!! info "Docker не нужен, MinIO/ClickHouse/Mongo моделируются"
    Скрипт ищет `infra/clickhouse/01_fact_readings.sql` и читает настоящий DDL,
    если репозиторий рядом. Запись идёт в локальный словарь: ключи те же, что у
    MinIO, но без сетевых таймаутов. Read-only пользователи ClickHouse/Mongo —
    backlog **SRV-23**; seed `provider_meta` — **SRV-22**.

### Ожидаемый результат

1. **События.** 5 провайдеров × 2 дня × 3 станции × 4 чтения = 120 событий;
   даты `2026-09-30` и `2026-10-01`.
2. **8.1.** `bronze` — 10 объектов (5 провайдеров × 2 дня), `silver` — 10,
   `gold` — 2; в каждом слое ровно 120 строк, пустых партиций нет.
3. **8.2.** 10 объектов, 120 строк; повторная запись даёт те же `checksum`,
   число объектов не растёт.
4. **8.3.** `engine=MergeTree`, `partition_by=toYYYYMM(dt)`,
   `order_by=(station_id, metric, measured_at)`; две партиции `2026-09` и
   `2026-10` по 60 строк.
5. **8.4.** Запрос `("stationId", "value")`: строка читает 720 значений
   (5760 байт), колонка — 240 (1920 байт), `speedup=3.0`.
6. **8.5.** `pv_meteo`: `TEMPERATURE`, `HUMIDITY` с диапазонами; `pv_air`:
   `PM2_5`, `NOISE` без диапазона. `PM2_5` находится, `OZONE` — `None`.
7. **Эксперимент.** Потеряно 60 строк, восстановлено 60, `restored=True`,
   отпечатки до и после совпадают.
8. Итог: `Итог: 7/7 проверок пройдено`.

!!! note "Почему 120 и 10 партиций"
    5 провайдеров × 2 дня = 10 объектов bronze. В silver ключ другой —
    датасет, но датасетов тоже 5, поэтому снова 10. Gold — витрина фактов,
    партиция только по дате: 2 объекта. Если числа не сходятся, проверьте,
    что путь строится из `providerId`/`datasetId`, а не из станции.


!!! note "«Колонки быстрее» — не про секундомер"
    На 120 строках разница в миллисекундах не видна. Мы считаем единицы чтения:
    строковое хранилище тянет все 6 полей, колоночное — только 2. На проде это
    превращается в гигабайты вместо мегабайт, но принцип тот же.


### Если что-то не работает

| Симптом                                             | Что делать                                                                 |
| --------------------------------------------------- | -------------------------------------------------------------------------- |
| 8.1: партиций 30, а не 10                           | ключ bronze — `providerId`, а не `stationId`                               |
| 8.1: в gold 10 объектов                             | gold партиционируется только по `dt`, а не по датасету                     |
| 8.2: `checksum` меняется при повторе                | сортируйте строки по `readingId` до сериализации                           |
| 8.2: объектов больше 10                             | путь должен быть детерминированным; проверьте, что не добавляете timestamp |
| 8.3: `partition_by` с лишними пробелами             | обрежьте выражение через `.strip()`                                        |
| 8.3: `order_by` — строка, а не кортеж               | проверка ждёт кортеж колонок                                               |
| 8.4: `speedup=6.0`                                  | в `column` посчитаны все `FIELDS`, а не только запрошенные колонки         |
| 8.5: `PM2_5` не находится                           | у `pv_air` метрики лежат в списке `metrics`, а не в `schema`               |
| Эксперимент: `missing=0`                            | в ключе должно быть `/{lost_dt}/`; проверьте формат путей                  |
| Кириллица в консоли ломается                        | `export PYTHONIOENCODING=utf-8`                                            |
| Студенческая версия печатает `0/7`                  | это ожидаемо до выполнения заданий; смотрите строки `Задание 8.x не выполнено` |
