# Семинар 7 — запуск и сдача

## Что внутри

| Файл           | Кому          | Что                                      |
| -------------- | ------------- | ---------------------------------------- |
| `seminar_07.py` | студенту      | задания с `# TASK` и `TODO`              |
| `README.md`     | обоим         | запуск, ожидаемый результат, диагностика |

Оба файла — IPython-скрипты: ячейки разделены `# %%`, markdown-ячейки —
`# %% [markdown]`. Открываются в JupyterLab, VS Code, PyCharm и запускаются
как обычный Python-скрипт.

## Подготовка стенда

```bash
git clone https://github.com/yanchick/Sputnik-Mart.git ~/Sputnik-Mart
cd ~/Sputnik-Mart
uv sync --all-packages --dev
```

!!! info "Docker и Airflow не нужны"
    Все задания вычислительные. Скрипт ищет `docker-compose.yml` и `dags/`,
    чтобы прочитать настоящие DAGи; если репозитория рядом нет, используется
    встроенный снимок тех же пяти DAGов. Управление DAGом через REST —
    backlog **SRV-19** (`scripts/airflow_client.py`); без него семинар
    воспроизводим.


## Запуск

### Вариант 1 — из терминала

```bash
export SPUTNIK_REPO=~/Sputnik-Mart
# из корня репозитория
cd "code/seminars/07_orchestration"

# студенческая версия (все 7 проверок FAIL до выполнения заданий — это ожидаемо)
uv run --project "$SPUTNIK_REPO" python seminar_07.py

```

`--with` не нужен: скрипт использует только стандартную библиотеку.

### Вариант 2 — JupyterLab

```bash
cd ~/Sputnik-Mart
uv run jupyter lab
```

Откройте `seminar_07.py` как notebook (JupyterLab понимает percent-format).
Выполняйте ячейки сверху вниз. Переменные `EVENTS`, `DAG_MAP`, `GOLD`,
`ETL`, `ELT`, `TRIAGE_RESULT` и `EXPERIMENT` объявлены в блоке «Прогон»,
поэтому ячейки можно запускать повторно.

## Ожидаемый результат

1. **События.** 3 дня × 4 батча × 3 станции × 8 значений = 288 событий плюс
   4 повторные доставки = 292; уникальных `readingId` — 288.
2. **7.1.** Пять DAGов, 13 задач. `ingest_readings`: `@hourly`, `catchup=False`,
   `retries=3`, порядок `wait_for_bronze → pull_bronze → validate → silver →
   transform → load_gold`. `retention_pii` — одна задача `delete_expired_pii`.
3. **7.2.** `received=292`, `total=288`; повторный прогон оставляет `total=288`.
4. **7.3.** `120 → ready/run`, `900 → wait/reschedule`, `2400 → fail/alert`.
5. **7.4.** Агрегатов 9 (3 дня × 3 станции). ETL `client_rows=301`
   (292 + 9), ELT `client_rows=9`; `digest` совпадает.
6. **7.5.** Четыре ошибки уходят в `retry` (сеть, таймаут, `503`, `429`),
   две — в `terminal` (`SchemaMismatch`, `401`).
7. **Эксперимент.** Полный прогон обрабатывает 292 события, resume — 192;
   `digest` одинаковый, `total=288`.
8. Итог: `Итог: 7/7 проверок пройдено`.

!!! note "«292 против 288» — это и есть at-least-once"
    Kafka доставляет повторно, поэтому 292 принятых события — норма. Вопрос не
    «как не получить дубли», а «почему повтор не меняет витрину». Ответ: ключ
    `readingId` и upsert по `receivedAt`.


!!! note "`catchup=False` — не мелочь"
    При `catchup=True` после простоя Airflow попытается догнать все пропущенные
    интервалы и создаст шторм прогонов. На демо-стенде это выглядит как
    «оркестратор сошёл с ума», хотя он делает ровно то, что просили.


## Диагностика

| Симптом                                             | Что делать                                                                 |
| --------------------------------------------------- | -------------------------------------------------------------------------- |
| 7.1: `source="snapshot"`, хотя репозиторий есть     | `SPUTNIK_REPO` должен указывать на каталог с `docker-compose.yml` и `dags/` |
| 7.1: задач меньше ожидаемого                        | парсер читает `>>`-цепочки и `task_id`; проверьте, что DAG не переписан     |
| 7.2: `total` растёт на повторном прогоне            | сравнивайте `receivedAt` строками ISO и заменяйте при `>=`                 |
| 7.3: `fail` вместо `wait` на 900                    | 900 больше SLA, но меньше таймаута; проверьте порядок условий               |
| 7.4: `digest` не совпал                             | ETL и ELT должны агрегировать одни и те же значения, разница только в `client_rows` |
| 7.4: `client_rows` равны                            | в ETL забыли прибавить загруженные агрегаты                                |
| 7.5: `HTTP 429` уходит в `terminal`                 | `429` — временная ошибка, проверяйте terminal-маркеры раньше retry          |
| Эксперимент: `resume` обработал столько же          | сравнение `dt > checkpoint_day` строгое; чекпоинт — последний загруженный день |
| Кириллица в консоли ломается                        | `export PYTHONIOENCODING=utf-8`                                            |
| Студенческая версия печатает `0/7`                  | это ожидаемо до выполнения заданий; смотрите строки `Задание 7.x не выполнено` |
